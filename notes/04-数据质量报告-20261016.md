## 二、按业务域的实测要点

### 展商域
- `expo_exhibitors` 主表 3,693 行，其中 `exhibitors020_1`（展位费）**3,683 行为空/NULL，仅 10 行是纯数字，0 行带逗号** → 该列基本弃用，金额真值在 `expo_exhibitors_fenpeizw` 的 ZW* 三列。
- `expo_exhibitors_fenpeizw` 2,631 行：`ZWZJ/ZWDJ/ZWYK` 三列是**带千分位的字符串金额**，必须 `REPLACE(x,',')::numeric` 处理；且存在 `''` 空串。
- `bs_city` / `bs_area` 虽为 latin1 列，实测存的是**行政区划代码**（如 `330300`），非中文名 → 无乱码风险，但需与 `geo_dict` 关联还原名称。

### 财务域
- `expo_financial`（收款流水）**0 行**、`expo_bank` 1 行、`expo_bank_deposit` 1 行、`expo_invoice_check` 0 行。
- 真实载体：`expo_financial_dues` 1,095 行（8 把区块锁的字段族）+ 视图 `v_get_expo_financial_dues_infolist` 3,701 行 + `expo_invoice` 1,602 行 + `expo_refund_deposit` 2,665 行。
- dues 的金额列大量空串（`dj_bffk` 1,095 行中 993 行为 `''`）→ 清洗规则：空串→NULL，再 `::numeric`。
- **五张报表的对账基准必须落在 dues + 视图口径上**（见 notes/02 Q6）。

### 订单域
- `expo_order_list` / `expo_order_pay` / `expo_site_order` **全部 0 行**；但字典 `expo_order_types_big/small` 有数据且 2026-05 仍在改。

### 观众域

## 三、要写的清洗规则（有限条数，可直接实现）

1. **千分位金额**：`nullif(trim(x),'')` → `replace(..., ',', '')` → `::numeric(12,2)`；适用 `fenpeizw.ZWZJ/ZWDJ/ZWYK`、`dues` 全族、`exhibitors020_1`、`payment1_amount/payment2_amount`。
2. **零日期**：`('0000-00-00'|'0000-00-00 00:00:00'|'')` → `NULL`；适用所有 date/timestamp 语义列。
3. **空串占位**：数字/日期语义列的 `''` → `NULL`（区别于真正的 0）。
4. **NUL 还原**：`\x00` 标记 → 视目标列决定丢弃或替换为空格，并在 `etl.load_error` 留痕。
5. **多值码表拆分**：`ZPLB` 等逗号串 → 数组或关联表（新模用 `text[]` 或 JSONB，需产品确认是否要按类别检索）。
6. **latin1 列复核**：`expo_admin.m5_1/m5_2`、`expo_enterprise.exhibitors015_3~6` 逐列取样本验中文（主库中文已验证安全，这几列尚未取到样本）。

## 四、纠错记录（我自己的两次误判，留此警示）

1. **第一版画像用列名启发式判"金额列"**，正则未覆盖 `ZWZJ/ZWDJ/ZWYK`，于是报出「金额带千分位逗号 = 0 命中」，与 `plans/05` §2 的既有判断冲突。改为**全列无差别扫描**后实测 51 列 / 11,826 行命中 → **文档是对的，我的探测方法是错的**。教训：脏数据结论不得依赖列名猜测。
2. **同版把 `payment*_date`、`ident_date` 误判为数字列**（正则含 `pay`/`num`），虚报「数字列存非数字 47,339 行」。加 `!DATE_HINT` 后降为真实的 22 列 / 450 行。
3. 扫描结果表 `etl.comma_scan_hit` 主键最初漏了 `source_db`，导致 `printingexhibition` 与 `dev_ems_print` 的同名同表同列互相覆盖、归属错乱；已改主键为 `(source_db, legacy_table, column_name)` 并重跑。
