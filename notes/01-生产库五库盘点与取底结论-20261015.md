## 三、「为什么这么小」的五个实证原因

1. **观众与预登记数据不在本实例**：`expo_visit` 90 行、`expo_visit_b` 109、`expo_visit_c` 107、`expo_visitor_online` 101、`expo_visit_r` 18。与 `plans/05` §2 生产实测一致——有效预登记走外部 **CIEC 平台**（data.ciec.com.cn），所以「18 年十万级观众」从来不在老库里。
2. **老库本质是台账型管理库**，不是 C 端流量库：展商 3,693、合同 395、审批节点 1,218、发票 1,602、退款押金 2,665、展位分配 2,631、资料主档 5,563。千行级。
3. **体量约三分之二是备份垃圾**：57 张 `_bak/_copy/_temp` 表（`printingexhibition` 51 张 30.8MB + `w_pte` 6 张 16.4MB）。
4. **三个功能域是空表**（重要）：
   - `expo_financial` **0 行**、`expo_financial_site` 0、`expo_financial_temp` 0、`expo_invoice_check` 0、`expo_bank` 1、`expo_bank_deposit` 1
   - `expo_order_list` **0**、`expo_order_pay` **0**、`expo_site_order` **0**
   → 收款流水表与在线订单实际未启用。财务数字的真实载体是 `expo_financial_dues`（1,095 行）+ 视图 `v_get_expo_financial_dues_infolist`（3,701 行）。
5. **压缩比正常**：104.5MB 未压 → 17.3MB gzip，与文本型 MySQL dump 的常规 5–8 倍压缩率一致，不存在「导漏了」。

## 四、字符集专项核查（差点踩雷，结论：主库安全，`print` 库已坏）

- 库默认字符集是 **latin1**（5 个库都是），但列级实际分布：`utf8` 3,368 列、`utf8mb4` 29 列、**`latin1` 24 列**、`utf32` 1 列。
- **主库中文未损坏**：抽样 HEX `334D E4B8AD E59BBD` = "3M中国"，为正确 UTF-8 字节；公司名含 `?` 的行数 **0**、简介含 `?` 的行数 **0**；公司名含中文 3,593 / 3,693 行。
  （排查过程中一度看到 `3M??`，经查是**终端渲染**问题，非数据问题。）
- `bs_city` / `bs_area` 虽为 latin1 列，实测存的是行政区划**代码**（如 `330300`），不含中文 → 该处风险解除。
- **仍需逐列验证的 latin1 列**：`expo_admin.m5_1`、`expo_admin.m5_2`、`expo_enterprise.exhibitors015_3 ~ _6`、`expo_order_list_temp.tonet/plan`、`expo_show_bak_20250727.s_bankid`、`expo_exhibitors_previous.note1`（utf32）。
- **真雷**：`print` 库 1,275 篇文章标题全为 `??????`，属 latin1 写入时丢字，**不可逆**，只能作废弃件归档。

## 五、隐藏写逻辑：2 个触发器

```
trg_contract_update_s…   （合同表状态更新触发器）
trg_invoice_update_s…    （发票表状态更新触发器）
```

以 `/*!50003 CREATE*/ /*!50017 DEFINER=…` 版本注释形式存在于 dump 中。二者都是**状态位的隐式写入点**，属于 §6.2「状态机显式化」必须吃掉的对象——之前 26 份代码梳理文档完全没有它们。**结论：老系统「谁改了状态」的谜团又多两处来源，报表与状态口径必须连同触发器一起还原。**

对象数与 `information_schema` 实测完全吻合（第二节的表/视图/过程/函数/触发器逐项对得上）。

解析过程中修掉的三个真实缺陷（都来自 mysqldump 的方言细节，值得记住）：

1. mysqldump 会为每个视图额外写一条「表形占位语句」，按语句计数会让视图数**翻倍** → 改为按 `kind|name` 去重、保留最完整的 DDL。
2. 触发器名在 dump 里**不带反引号**（`/*!50003 TRIGGER trg_x BEFORE INSERT …`），要求反引号的正则永远匹配不到 → 放宽并锚定 `BEFORE|AFTER|INSTEAD`。
3. 视图定义被拆成 `/*!50001 CREATE ALGORITHM…*/` + `/*!50013 DEFINER…*/` + `/*!50001 VIEW … */;` 三行，必须按 `DELIMITER` 感知的缓冲逻辑跨行聚合，不能逐行判定。
